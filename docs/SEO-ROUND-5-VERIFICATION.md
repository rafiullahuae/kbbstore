## 1. The method, and why this round exists

Four rounds of SEO work were reported as done, and every report leans on a
document written at a point in time. **A document is not evidence.** So no verdict
in this round was copied: each item was driven against the running shop and the
verdict computed from what came back.

**And the matrix asserts itself.** Every row whose verdict is decidable by
measurement computes it and then asserts it. A regression in any of them turns
`SeoPreviewsTest` red rather than quietly making the preview say the opposite of
the shop. That includes the seven STALE rows: each is phrased as *"the document
says missing, and here is the measurement proving it is built"*, so the day one of
them is un-built the file goes red. (It did not start that way — the Journal
`CollectionPage` row survived its mutation as an authored string, which is exactly
the hole this paragraph describes. All seven were converted.)

## 3. The defect this round found, and fixed

**A content page's own SEO fields were written by the admin and read by nothing.**

`pages` carries the same `{title, desc, og_image, canonical, noindex}` column that
`products`, `categories`, `brands` and `posts` carry.
`Store\PageController::show()` passed the view a row and **no SEO context at all**,
so all seven routed content pages took the layout's defaults. Measured on a running
server, with every field saved on the `faqs` row:

```
seo.title     "OVERRIDE TITLE"     ->  <title>Frequently Asked Questions · K-Beauty Bliss</title>
seo.desc      "OVERRIDE DESC…"     ->  <meta name="description" content="…the SITE-WIDE default…">
seo.canonical "/somewhere-else/"   ->  <link rel="canonical" href="…/faqs/">
seo.noindex   true                 ->  <meta name="robots" content="index, follow">
/sitemap.xml                       ->  still carried <loc>…/faqs/</loc>
```

**The last two lines are the ones that matter.** `SeoAudit::scanPages()` *skips* a
page whose `seo.noindex` is set — it treats the row as deindexed and stops
auditing it. So Store → SEO & Meta → SEO Audit reported the page as out of the
index *because the owner had asked for that*, the page went on inviting the crawl,
and the sitemap went on submitting it. Two documents agreeing with each other and
both disagreeing with the owner, with the one screen that could have shown it up
quietly looking away. That is the shape of the `/cart` leak `CLAUDE.md` records.

Both halves fixed, in two files:

- `app/Http/Controllers/Store/PageController.php` — `show()` now builds a
  `$seoCtx` from `pages.seo`. **Every key is conditional**, so a page with no
  override renders byte-for-byte what it rendered before.
- `app/Http/Controllers/Store/SeoFilesController.php` — the pages query now
  selects `seo` and skips a noindexed row, which is what `isNoindex()`'s own
  comment already said the rule was ("a page that sets noindex must drop out of
  this file whichever table it lives in").

Ten cases in `tests/Feature/PageSeoOverridesTest.php`, the first two of which are
the rule-1 cases: an untouched page, and a page whose override is all empty
strings (which is what the panel writes for a field nobody typed in).

## 4. What was built

### `FAQPage` — `app/Services/Seo/FaqSchema.php`

**Confirmed missing** before this lane: `grep -rn FAQPage app resources routes
tests` returned nothing, and `/faqs/` emitted `Organization` and `WebSite` and
nothing else.

**The three rounds of refusal are answered rather than ignored.** The rich result
is genuinely gone — Google stopped showing FAQ drop-downs on 7 May 2026 and
`SEO-COMPETITIVE.md` §1.9 is right about it, **and nobody should be promised
one**. What is built is the thing that refusal did not weigh: the machine-readable
question/answer *pair*, which is the unit an answer engine extracts and which an
`<h3>` above a `<p>` is not. It is one node on one page, valid schema.org whatever
Google renders, and it is off.

Design points worth knowing:

- **The source is the page's own body.** No new editor, no new table. That is the
  rule Google actually enforces about this markup — the marked-up questions must
  be the ones a visitor can read — and a second copy of the text would disagree
  with the page within a month.
- **A heading counts as a question only if it ends in `?`.** That single rule is
  the whole page selection: no slug is named anywhere in the class. The shipped
  `/faqs/` produces four pairs; the shipped `/refund_returns/` ("What we need from
  you", "Refunds", "Your rights") produces none. Rewrite either page and the
  answer changes with it.
- **Plain text, tags stripped** — an answer carried through verbatim would put
  operator-authored `<a href>` into a document handed to a search engine. A
  `<script>` element is stripped with its contents, so the payload is absent as
  well as inert.
- **Refusals**: fewer than two usable pairs → no node; more than 24 question
  headings → no node (the rule has misread the page); an answer under four words
  or over 1,200 characters → that pair is dropped, **never truncated**, because a
  truncated answer is an answer the page does not give.
- **Encoded with the same four HEX flags** `Support\Seo::encodeJsonLd()` uses, and
  a case drives a `</script><script>` payload through both encoders.

**Ships OFF.** `SeoSettings::DEFAULTS['faq_schema'] = '0'`, so the package moves no
page by a byte. Fifteen cases in `tests/Feature/FaqSchemaTest.php`.

### The crawl-surface completeness guard

`tests/Feature/CrawlSurfaceCompletenessTest.php`. `SeoCrawlSurfaceTest` walks
sitemap → shop. **Nothing walked shop → sitemap**, which is the direction
`/_design-check` escaped in for eighteen phases while
`SEO-FEATURE-MATRIX.md` listed crawl hygiene as something this shop *wins* on.

It asks the router for every parameterless storefront GET route, fetches each, and
fails on a 200 HTML page that declares `index` and is absent from the sitemap.
Exactly one deliberate exception today — `/reviews/` while the shop has no approved
review — and a second case asserts the exception **discharges**: one approved
review and `/reviews/` is submitted. A third case asserts the whole set of HTML
pages that declare nothing about indexing (`/up`, Laravel's health endpoint, and
nothing else), so a new one is a failure rather than something nobody looked at.

## 5. Needs Lane S5 — `app/Support/Seo.php`, with the exact change

### 5.1 `Article` carries no `dateModified` and no `url`

`dateModified` is on Google's recommended list for `Article` and `posts.updated_at`
is right there. `mainEntityOfPage`/`url` gives the node an identifier.

**ANCHOR** (`app/Support/Seo.php`, in `jsonLd()`, the Article branch):

```php
                'headline' => $a['title'] ?? $title,
                'image' => $image ?: null,
                'datePublished' => $a['published_at'] ?? null,
```

**REPLACEMENT:**

```php
                'headline' => $a['title'] ?? $title,
                'image' => $image ?: null,
                'url' => $url,
                'datePublished' => $a['published_at'] ?? null,
                'dateModified' => $a['updated_at'] ?? null,
```

`array_filter()` already wraps the node, so a post with no `updated_at` emits
neither key and nothing moves. The caller half is
`Store\PageController::post()`, which is not S5's — it needs
`'updated_at' => optional($post->updated_at)->toAtomString(),` beside
`'published_at'` in the `article` array. **Both halves or neither**: the Seo change
alone is inert, which is the safe direction.

### 5.2 A canonical override is not scheme-checked before it becomes an `href`

`Seo::canonicalAbsolute()` returns any `scheme:` value verbatim, so a per-row
canonical of `javascript:alert(1)` is published in `<link rel="canonical" href>`,
`og:url`, `Product.url` and the hreflang hrefs — on products, categories, brands,
posts and (as of this lane) pages alike.

**Severity is low and should be stated as low**: a `rel=canonical` href is not
navigable, everything is `htmlspecialchars`-escaped with `ENT_QUOTES` so it cannot
break out of the attribute, and `SeoAudit::canonicalIsSafe()` already *reports* it
under "Canonical points somewhere unsafe". But `CLAUDE.md` rule 5 says in as many
words: *"A URL from a setting is scheme-checked before it becomes an href."*

**ANCHOR** (`app/Support/Seo.php`, in `canonicalAbsolute()`):

```php
        if (preg_match('#^([a-z][a-z0-9+.-]*:|//)#i', $url) === 1) {
```

**REPLACEMENT:**

```php
        /*
         * A scheme this shop will not publish. The per-row canonical override is
         * a setting-shaped value that becomes an href, an og:url and a node
         * identifier, so the scheme is checked here rather than trusted -- the
         * same rule SeoAudit::canonicalIsSafe() already applies when it REPORTS
         * one. Anything that is not http, https or protocol-relative falls
         * through to the path branch below, which produces an address on this
         * site instead of the operator's string.
         */
        if (preg_match('#^(//|https?://)#i', $url) === 1) {
```

The case to add with it, in whichever `tests/Feature/*Seo*` file S5 is holding:
a product with `seo.canonical = 'javascript:alert(1)'` publishes a canonical on
this site and the string `javascript:alert(1)` appears nowhere in the `<head>`.
**This lane deliberately did not pin the defect as-is** — a pin would have to be
removed when S5 lands the fix — and `PageSeoOverridesTest` says so in its own
comment.

### 5.3 The FAQPage node needs one call to be live

`FaqSchema` is complete and tested and emits nothing, because the one place a node
can join the graph is `Seo::jsonLd()`.

**ANCHOR** (`app/Support/Seo.php`, in `jsonLd()`, immediately before the
`// Breadcrumbs` comment):

```php
        // Breadcrumbs
```

**REPLACEMENT:**

```php
        /*
         * FAQPage, from the questions a content page already answers.
         *
         * Off unless Store -> SEO & Meta -> "FAQ markup" is on, and null unless
         * the page is genuinely written as questions -- see Services\Seo\FaqSchema
         * for why the question mark is the whole selection rule, and why no page
         * slug is named anywhere. Merged into THIS graph rather than emitted by a
         * second class, for the reason SEO-BUILD-PLAN item 3 refuses a SeoGraph:
         * two emitters is two Organization nodes on every page.
         */
        if (($ctx['type'] ?? '') === 'page'
            && \App\Services\Seo\FaqSchema::enabled($s)
            && ($faq = \App\Services\Seo\FaqSchema::node((string) ($ctx['page_body'] ?? ''), $url)) !== null) {
            $nodes[] = $faq;
        }

        // Breadcrumbs
```

The caller half is `Store\PageController::show()` (this lane's change, already in
place): add `'type' => 'page'` and `'page_body' => (string) $page->content` to the
`$seoCtx` it builds. **This lane did not add those two keys**, because an unread
`type => 'page'` would be inert but an unread `page_body` on a shop whose flag is
on is a promise the graph does not keep — so both halves land together, in S5's
package, and `FaqSchemaTest` is green either way.
